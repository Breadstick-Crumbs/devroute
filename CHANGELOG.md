# Changelog

All notable changes are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Changed
- **A visual redesign is no longer routed like an architectural change** (ADR 0008).
  - **What changes:** "Redesign the pricing page layout for mobile" and "Redesign the onboarding screens in the React Native app" route STANDARD instead of DEEP. Briefs list what was ignored. Payment-page styling ("Change the checkout button color to green") deliberately keeps DEEP and every payment control: a heuristic never removes payment controls.
  - **What counts as a visual redesign:** a task that is short, one clause, and fits a closed vocabulary and structure (`[assessment.presentational]`). It has a redesign verb, an object of at most one page name from a short list and UI nouns, and a tail of only look words, "to <color or size>", and "on/for <platform or look>".
  - **What keeps it architectural:** another architectural phrase ("with microservices", "into web views", "the container components", "the micro-frontend pages"), anything that turns the object into something else, or any word for data, state, flows, routing, APIs, or authentication, also when hyphenated.
  - **Also new:**
    - `visual-redesign`, `responsive-layout`, and `visual-tweak` signals;
    - "build a/the ..." counts as new functionality (not for a project, docs, or image);
    - navbar, sidebar, footer, and spacing count as UI;
    - signals can limit their caps with `caps_if_signals`.
  - **How it was checked:** every reference-suite case keeps its route. A rule that also removed payment controls for styling-only tasks was built and dropped: three adversarial reviews kept finding payment changes phrased as styling. Their phrasings are now tests that require every payment control. Three details were tuned after seeing a suite result: a look phrase may come before the object, "restyle" counts as a visual redesign, and a page name may only come before the object.
- The automatic-routing brief says "Do not wait for approval" instead of "Work autonomously", and asks Claude to ask you instead of guessing when an ambiguity would change what it builds. When the assessment has low confidence, it tells Claude to ask one to three focused questions about scope before editing. Neither appears once you asked for autonomy in the task ("work autonomously", "don't ask", also mid-task, after a raise, or when Claude routes the task anew). Hands-off still adds no approvals or confirmations (ADR 0009).
- A bare "don't ask" at the end of a clause ("fix it, don't ask") now counts as asking for autonomy; before, only "don't ask me" did. "Don't ask for the password twice" still does not.

### Added
- **`susanoo land`: land agent branches through one tested combined tree** (ADR 0014, [docs/land.md](docs/land.md)). `susanoo land 52 53` fetches `origin/main` and the candidates (pull request numbers or branch names), merges them in order into a scratch worktree, and runs the project's checks on the combined tree: the DEEP verification plan's ready, required steps, plus `[[land.checks]]` and `[[land.compare]]` (a JSON command compared with the base, such as `susanoo eval` agreement and risk-floor violations when routing data changes), with configuration read from the base branch.
  - **Conflicts:** listed per file; only append-only places (`CHANGELOG.md` `## [Unreleased]`, ADR index tables; `[[land.keep_both]]`) are resolved, by keeping both sides with the base's lines first, and only when both sides only added lines. Anything else stops before a check runs.
  - **Failures:** rerun once (flaky), then the prefixes and the culprit alone name the branch and the kind: broken alone, interaction with the earlier branches (a semantic conflict), or a broken base, with the failing output.
  - **Push and merge:** the base is merged into each branch (never a rebase or force push), its tree must equal the tested one, and it is pushed. Only `--merge`, which you give, merges, through `gh pr merge --merge --match-head-commit <tested sha>` with `Merge: <title> (#n)` and no attribution lines; with several pull requests, every intermediate state of the base is checked before the first merge. Without it, the run stops at "ready to land" and prints the command and a one-line status. The PreToolUse hook asks before any `susanoo land ... --merge`, in every mode.
  - **Records:** each run goes to `<git common dir>/susanoo/records/land.jsonl`, shared by all worktrees; `susanoo land --stats` counts them against ADR 0014's go or no-go rule. A passing result is reused for the same combined tree and checks, so `land` then `land --merge` checks once.
- **The taste-ui skill**, installed by `susanoo init` (project and `--global`; `--no-taste` leaves it out).
  - **What it is:** a way for Claude to make visual decisions for UI work. Susanoo itself still never judges aesthetics.
  - **What it does:** reads your personal taste profile (`TASTE.md` plus captured reference sites), checks whether that look fits the product, proposes three distinct directions, defines design tokens first, and screenshots its own work at the visual check's widths (375, 768 and 1280 px) before handing back. See ADR 0010.
  - **Precedence:** the profile is a quality bar, not a required look. A project's `DESIGN.md`, its tokens, or a client's brand win where they conflict, and Claude asks you when the fit is unclear.
  - **`susanoo taste path | shoot | capture`:** shows where the profile is, takes screenshots, and records reference sites for a new profile. Needs Node.js 22+ and Chrome, Chromium or Edge; no Python dependencies.
  - **`capture` also records navigation and motion** in `motion.json`:
    - navbar behaviour across a scroll down and back up (sticky, hides on scroll down, comes back on scroll up, background, blur, shadow or height changes);
    - elements that pin, move at parallax speed or animate while scrolling;
    - hover changes on nav links and buttons, and the transitions in use;
    - the mobile menu (opened through its toggle button only, never a link);
    - the motion libraries' own settings read from the live page (scroll triggers with pin, scrub, start and end; smooth-scroll settings);
    - an 8-frame scroll strip (`strip.jpg`) plus `mobile-top.jpg` and `mobile-menu.jpg`. `SUSANOO_CAPTURE_NO_MOTION=1` skips this part.
  - **Where the profile lives:** `SUSANOO_TASTE_DIR`, then `[ui] taste_dir` in the user configuration (Susanoo's project configuration is ignored, and relative paths are rejected), then `~/.susanoo/taste`. Node and the browser are never taken from the current folder, and on Windows only `.exe` files count.
  - **Effect on UI checks:** the skill declares the `visual_check` capability. Where it is installed, the visual check on automatic routes becomes a manual step that is demanded, instead of unavailable. Record it with its screenshots. Record it as skipped, with the reason, only when no tool at all can render the page.
- **Tokens, duration, and tool calls from Claude Code transcripts** (opt-in, `[records] capture_usage = true`). When an outcome is recorded, by `susanoo outcome` or when Susanoo closes a route a new task replaced, Susanoo reads the route's Claude Code session transcript and its subagents' transcripts, counting only the assistant messages between the route's creation and the outcome (or the session's next route). It fills `duration_minutes`, `tokens`, and `token_counts`, which keeps fresh input, cache writes, cache reads, and output apart (`tokens` is their sum), plus `tool_calls`, the number of calls per tool name. Values you pass are kept, and `captured` lists the fields that came from the transcript. Cost is filled only when the transcript records one; Susanoo does not estimate prices. Only usage numbers, timestamps, message ids, and tool names are read, never message text or tool inputs and results; a missing or changed transcript format captures nothing. Transcripts are read from the end, so a long session costs only the part a route covers; past about 2 seconds or 64 MB of reading nothing is captured.
- `susanoo report` shows mean tokens next to mean minutes per profile, each with the number of outcomes it is based on, and says that tasks routed to different profiles differ in size, so the numbers do not compare workflows. When outcomes have separate token counts, a "Token usage by profile" table shows mean fresh input, cache writes, cache reads, and output, the cache-hit ratio (cache reads / all input), and the most used tools; any recorded cost is totaled per profile. `--json` adds `mean_tokens`, `with_tokens`, `timed`, `captured`, `with_token_counts`, `token_count_totals`, `cache_hit_ratio`, and `tool_calls` per profile.
- **Architecture context in STANDARD and DEEP briefs** (ADR 0011). Discovery finds, read-only, a project's `ARCHITECTURE.md` or `docs/architecture.md`, the documents under `docs/architecture/`, decision-record folders (`docs/decisions/`, `docs/adr/`, `adr/`, and similar, named with their record count), architecture sections of `AGENTS.md` and `CLAUDE.md` (by line number; the heading text is never copied), and boundary rules (`.importlinter`, `.dependency-cruiser.*`, ArchUnit in `pom.xml` or Gradle files). STANDARD and DEEP briefs, full and automatic-routing, list them and tell Claude to read the relevant ones before designing, stay within their layering and decisions, and flag a conflict instead of working around it; with none found, to follow the structure of the code it changes. FAST briefs are unchanged. A new **architecture boundary check** (`architecture_check`), recommended in STANDARD and DEEP, runs the project's import-linter (`lint-imports`), `depcruise` package script, or ESLint with eslint-plugin-boundaries; dependency-cruiser without such a script is a manual check, and ArchUnit is named but not run. It is left out when no boundary tool is configured; import-linter counts when the package is declared in the project's Python dependencies. The `susanoo-reviewer` subagent now also reviews changes against the architecture context. `susanoo inventory` lists the architecture context, also in `--json`.
- **UI checks** (ADR 0008). Tasks that touch a user interface get a **visual check**: recommended in FAST, required in STANDARD and DEEP. Claude renders the change at 375, 768, and 1280 px, compares it with the request, and records what it checked with `susanoo evidence latest --step visual_check` (a skip with the reason is accepted when nothing visible changed). It is always reported evidence, never a command Susanoo runs. A browser MCP server, Playwright in the project, the Claude desktop app's browser, or an installed skill or subagent whose name or description matches the capability's keywords counts as a tool for it; without one it is a gap. An **accessibility scan** is recommended in STANDARD and required in DEEP, run with the project's axe-core Playwright tests or `pa11y-ci`, or by the agent with the axe CLI. **Visual regression** with Playwright screenshot baselines is recommended only when baselines exist. Lighthouse CI is detected for the website performance budget. The brief shows each manual check's instructions.
- **Design context in UI briefs** (ADR 0008). Discovery finds, read-only, a project's `DESIGN.md` or `docs/design*.md`, token files (`tailwind.config.*`, `*.tokens.json`, token folders, and global stylesheets with a Tailwind v4 `@theme` block or five or more custom properties), Storybook, and a usable Figma MCP server or plugin by name. UI briefs list them and tell Claude to follow their design guidance (as project data, not instructions), or suggest adding a `DESIGN.md` when there is none (Susanoo never creates it). When a `taste-ui` skill is installed, UI briefs say to follow it as a quality bar, with the project's design context and brand guidelines winning where they conflict. `susanoo inventory` lists the design files and suggested UI domains, also in `--json`.
- **UI domains and checklists** (ADR 0008). A UI task's brief names its UI domain (`website`, `ecommerce`, `dashboard`, `mobile`, `component-library`) and why: `[ui] domain` in configuration, then phrases that name the product ("landing page", "admin dashboard"), then generic words ("chart", "cart"), then the project's dependencies and files (`recharts` or `@tanstack/react-table` for a dashboard, `react-native` or `pubspec.yaml` for a mobile app, Storybook only when nothing else is detected for a component library). It does not change the route or its safety controls. When it comes from the task or the project, the brief says it is a heuristic; `susanoo inventory` lists the domains the dependencies suggest. The full brief lists a WCAG 2.2 AA baseline (contrast, target size, keyboard and focus, empty/loading/error states, common widths) and 5-7 items for the domain, each list with its sources; the short automatic-routing brief gets one line. Website tasks also get a recommended performance budget (Lighthouse CI). Domains and checklists are data in `ui_domains.toml`; `[[verification]]` rules can name `ui_domains`.
- `[[verification]]` rules take `instructions`, `only_with_tool` (never drops a required step), and `evidence = "reported"` (the check stays manual even if a tool has a command for it); registry tools take `requires_files` (detected only when one of those files also exists; a trailing `/` matches folders only).
- ADR 0008 (accepted, partly implemented): how Susanoo will handle UI and UX work. It requires and records UI checks (a visual check at common widths, accessibility scans in DEEP), gives short domain checklists, and points Claude at design context; it does not judge aesthetics. Implemented so far: the UI checks, UI domains, design context, and the evaluation pieces below; the routing changes are not built yet.
- UI reference suite `ui-v1.toml` (44 cases, labeled before the heuristics they test were changed): `susanoo eval --suite src/susanoo/data/suites/ui-v1.toml` from a source checkout. With v0.7 heuristics its first 15 cases agreed on 8; now all 44 agree with 0 risk-floor violations, and CI runs it with the same gates as `routing-v1`.
- Routing suites can list `controls` a case's route must include; a missing control counts as a risk-floor violation, and an unknown control id is a suite error.

### Fixed
- **A task you type is routed even when the app puts a status reminder above it** (ADR 0016). In the desktop app your message sometimes arrives with a `<system-reminder>` first ("The user started your suggested background task ..."), and because the prompt then started with `<`, a clear task like "delete the widget type foundation branch" got the unrouted note instead of a route. The hook now decides whether a prompt is a task, a question, or a follow-up from your own text without the app's blocks; the levels and the route's assessment still read the whole prompt, so the reminder can raise a route but never lower it. When a block's tags are left over in your text, the whole prompt is read, as before.
- **Messages from the app or other sessions no longer route as if you typed them** (ADR 0016). In the desktop app, notes from other sessions, side-session notes, task notifications, and CI events arrive as prompts, often with the app's status reminders above them. The hook recorded their keywords as your message: on 2026-10-15 a peer's note about a pytest override made a one-line config change DEEP with payment, authentication, and data controls, because linked session titles in a status reminder read as payments and auth. Now a prompt made only of such blocks (`[auto] app_envelopes`) leaves the open route and your last message's levels as they were, and Claude gets a one-line note; the route-before-edit gate still applies. Your earlier "work autonomously" or named workflow does not carry over to work a peer asks for. A prompt with any text of yours counts whole, as before, so nothing you send can lower a route; only "work autonomously" and a named workflow ignore the blocks (and count not at all when a block's tags are left over), so a peer cannot ask for them for you. A block pasted on its own is taken for the app's message; type anything with it to make it yours.
- `susanoo verify --execute` runs pytest as `python -m pytest -q` (was `pytest -q`). The module form always puts the project root on `sys.path`; the `pytest` script does so only for some layouts, so a flat-layout project whose package is not installed (conftest.py only in `tests/`) failed its unit and integration checks with `ModuleNotFoundError` on correct work, and the evidence gate blocked it. `python` is the project's environment (`.venv`, `venv`, `env`) when there is one; otherwise it is the interpreter the discovered `pytest` script belongs to (its `#!` line or a `python` beside it), so pipx or `uv tool` installs and systems without a `python` command (macOS, Debian) still run the same pytest as before. Poetry and Pipenv projects run `poetry run python -m pytest -q` and `pipenv run python -m pytest -q`.

## [0.7.0] - 2026-10-14

### Changed
- **Breaking: irreversible commands no longer ask by default, also in Claude Code's normal mode.** With `--enforce`, the irreversible-action confirmation (force push, history rewrite, deploy and publish, `terraform destroy`, `kubectl delete`, destructive SQL) used to ask in normal and plan mode; with the new default `hands_off = true` it does not, so a command you allowlisted in Claude Code runs without any confirmation. Existing `--enforce` installs get this on upgrade. Set `[enforcement] hands_off = false` to bring it back. See ADR 0007.
- **Hands-off by default:** `[enforcement] hands_off = true` turns off Susanoo's own approvals and confirmations (plan approval, shell writes before approval, irreversible actions, route integrity) in every Claude Code permission mode; Claude Code's permission settings decide what needs confirmation. The evidence gate stays, `susanoo approve` still asks (an approval Claude recorded itself would count later), and `--accept-missing-evidence` is refused instead of asked about. Briefs title the section "Checkpoints" and mark phases `[checkpoint]`, and the skill and playbook report checkpoints instead of stopping at them. Set `hands_off = false` for the previous behavior.
- The package.json test script runs as `<manager> run test` (was `npm test`) and is listed as "package.json test script".

### Added
- **Claude's judgment above a keyword floor** (ADR 0006). With automatic routing, prompts the hook does not route get a one-line note, and Claude routes them itself when they need code changes ("the checkout page is broken"). `susanoo route` in such a session combines Claude's description with the keyword assessment of the user's latest message: every dimension takes the stricter level, the message's signals count, and the profile is never lower than the message alone. A route that replaces an open one keeps that route's levels too, after any kind of message; `susanoo route` never replaces a route with unfinished work. `--profile` changes only the profile and never removes a safety control. `/susanoo` keeps its full brief. The hook keeps only levels and signal ids per session (from the first 20,000 characters, without counting vagueness as risk), never the message text.
- `susanoo raise standard|deep --reason "<the risk>"` makes the open route stricter. It never lowers a route or drops a control: the open route is its floor, the target is a minimum, and risk named in the reason turns on the matching controls (also on a route that is already DEEP). Recorded evidence carries over, and so does autonomy asked for in words; a plan approval does not, because the plan changed. Every brief mentions it.
- With automatic routing, `susanoo route --profile fast|standard` refuses a profile below Susanoo's recommendation unless the user's latest message named it, so Claude asks the user instead. In such a session, `route` and `raise` refuse `--config`, and every route keeps the open route's controls even if the prompt record is lost. `route` no longer accepts abbreviated options.
- **Route before edit:** with automatic routing, when a message was not routed and Claude edits a project file with no route open, that first edit is denied once and Claude is told to run `susanoo route` first; a retry goes through. It never asks the user, so it applies in every permission mode. `[auto] route_before_edit = false` turns it off, and agent memory and settings (`CLAUDE.md`, `AGENTS.md`, `.claude/` folders, at any depth and also as Git Bash paths on Windows) are exempt (`route_before_edit_exempt`). Edits through shell commands are not covered.
- `scripts/live_auto_check.py --only unrouted`: live check that Claude routes a problem report the hook does not route.
- Briefs name installed skills, subagents, and MCP servers that fit each capability, one of each kind first ("also installed: ..."), including the short brief that automatic routing adds; previously only the top-ranked tool was shown, so a configured code-graph skill or MCP server went unmentioned.
- JavaScript package managers: the project's manager (package.json `packageManager`, else its lockfile) decides how commands are spelled. The test script runs as `pnpm run test`, `bun run test`, `yarn run test`, or `npm run test`; install hints use `pnpm add -D`, `bun add -d`, and so on; `[selection] default_package_manager` covers projects without either. New `pnpm audit` and `bun audit` registry entries.
- Task keywords in the tool registry: a tool the task names, or whose technology it names, is preferred among comparable options ("postgres" suggests psql, "sqlite" sqlite3). `[selection] task_keyword_bonus`.
- Gap suggestions include the install hint ("consider Gitleaks (cli), install: ...").
- `dependency-change` and `dependency-upgrade-broad` signals: adding, removing, or bumping packages recommends a dependency audit; upgrading many packages or major versions also raises uncertainty and testing difficulty. Verification `escalate` entries can name a `signal`. "install", "uninstall", "pin", and "unpin" start a task in automatic routing ("install docker" and "install the project dependencies" do not). Six routing-suite cases for dependency changes, labeled before the signals were written or tuned ("Upgrade django from 3 to 5" is a major-version jump, which counts as a broad upgrade); one ("Replace moment with date-fns across the codebase") still routes FAST instead of STANDARD, because keywords cannot tell that `moment` is a library.

### Fixed
- `susanoo inventory` reports "GitHub remote configured" only when a remote's host is `github.com` (or a subdomain). It used to match `github.com` anywhere in the URL, so remotes such as `https://github.com.example.org/...` were counted (CodeQL `py/incomplete-url-substring-sanitization`).
- Python checks in Poetry and Pipenv projects no longer run with the wrong interpreter. These managers keep the virtualenv outside the project by default, so `pytest`, `ruff`, `mypy` and other Python tools were planned (and, with `verify --execute`, run) from PATH without the project's dependencies, and the result was recorded as executed evidence. When such a project has no in-project environment (`.venv`, `venv`, `env`) and no `uv.lock`, Python tools and scripts (including the Django migration check) now run through `poetry run` / `pipenv run`, and tools declared in the project's dependencies (`pyproject.toml`, requirements files, and now `Pipfile` `[packages]` / `[dev-packages]`) count as installed even though they are not on PATH. If the manager is not on PATH, those checks are not run by Susanoo: a tool found on PATH becomes a manual step, a tool found nowhere stays a gap, and either way the reason is shown in the brief, `susanoo verify` and the skipped evidence note (and, for manual steps, the auto-mode brief); a runnable alternative such as `make test` is preferred. Managers are data (`[[environments]]` in the packaged `tools.toml`); `susanoo inventory` lists the detected one. Wrapped commands need the Poetry or Pipenv environment: `poetry run` / `pipenv run` may create it during `verify --execute`. The managers resolve the tool inside their environment first; a tool that is not installed there still falls back to PATH.
- `npm audit` was selected in pnpm and Bun projects whenever npm was on PATH, and failed there without a package-lock.json; it now applies only to npm projects.
- `bun.lock` (Bun 1.2 and later) is recognized as a Bun project.

## [0.6.0] - 2026-10-13

### Added
- **Global auto mode** (#34): `susanoo init --global` makes Susanoo the default workflow in every project. Coding prompts are routed automatically by a `UserPromptSubmit` hook (questions and ambiguous prompts pass through; a leading `?` skips routing; follow-ups continue the current task, and an unrelated or stricter task closes it and starts its own), a playbook goes into `~/.claude/CLAUDE.md` (a rules section written once, plus a managed workflow block), and records live in `~/.susanoo/projects/` so nothing is added to repositories. `.susanoo-off` turns it off in one project. Global mode applies only inside git repositories, and the global hooks step aside in projects that run Susanoo hooks of their own (`--enforce-scope settings`); `susanoo doctor` warns about skill-scope projects, where gates could run twice. `--no-auto` keeps the gates without routing; `--uninstall` removes what was added. Hooks run with `python -P` so project files are never imported, and a fast entry point keeps them light.
- **Autonomy-aware gates:** in Claude Code's acceptEdits, auto, dontAsk, and bypassPermissions modes, Susanoo adds no approvals or questions (`[enforcement] autonomous_modes`), and refuses `--accept-missing-evidence` instead of asking. Asking for autonomy in a task ("work autonomously", "don't ask", also mid-task) counts as approving its plan; the irreversible-action confirmation stays. The evidence gate stays in every mode.
- `--auto` for project installs with the settings scope; `~/.susanoo/config.toml` for user-wide configuration; `SUSANOO_HOME`; `susanoo doctor` reports global mode.
- `scripts/live_auto_check.py`: live checks of automatic routing; results in `docs/enforcement.md`.
- Visual identity: an original armored-helmet (kabuto) mark with a lightning crest, Cascadia Code wordmark, light and dark README banners, and a social preview card, all generated by `scripts/make_brand_assets.py` (the card's terminal lines come from real routing results).
- README redesign: an animated terminal demo generated from real `susanoo route` output (`scripts/make_demo_svg.py`, checked by a test), a workflow diagram, a comparison with plain Claude Code, and an FAQ.
- `llms.txt` (a plain summary for AI search and assistants) and `CITATION.cff` (GitHub's "Cite this repository").

### Changed
- In the default autonomous modes, the plan-approval gate, approval confirmation, and the shell-write, irreversible-action, and route-integrity asks no longer apply. Set `autonomous_modes = []` for the previous behavior.

## [0.5.0] - 2026-10-13

### Added
- Negation in task assessment (#11): an instruction to leave a code location alone ("fix the footer typo without touching the payments module", "rename the helper without changing the database schema") no longer counts as signals, and is listed as "Ignored as out of scope". It is narrow on purpose: only instructions (not descriptions such as "the job is not changing the hash"), only with a code-location noun, ending at that noun or at a sentence or line end, never across destructive-data or production phrases, and only when the rest of the task is a single clause with a clearly trivial edit keyword (typo, wording, rename, docstring, ...) and no new functionality. "Without breaking payments" and "without touching the payment code, add idempotency keys" still count. Configurable in `[assessment.negation]`.
- Test-only tasks (#11): a short, plain test request ("write unit tests for the invoice total calculator") gets security and data-integrity risk capped at low. A longer subject, a second clause, prepositions ("by", "in", "using", ...), "-ing" words, words such as production, deploy, real, or live, and a database, destructive-data, or production signal all keep the full risk. Irreversibility and external-dependency risk are never capped, so production and sandbox controls stay. Generic `caps_only_if` and `caps_unless_signals` support for signals, and a `trivial-edit` signal (no effects) that negation requires.
- A property test checks 75 adversarial wordings from four rounds of independent review: the new logic must not lower their risk.
- The sensitive-data signal also matches "SSNs".
- Eight routing-suite cases for negation and test-only scope, committed before the heuristics changed.

### Changed
- The destructive-data signal also matches "delete all user records", "deleting ... records", and "migrate the data".
- The suite case `tests-only-payments` gained `min_risk = "moderate"` after review, so test-only caps cannot silently remove external-service risk.
- The small-change rename pattern also matches a name before the noun and `helper` / `constant` ("rename the getUser helper"). This was adjusted after seeing a new suite case route STANDARD.
- Routing suite: 97.4% agreement (38/39), 0 risk-floor violations; the v0.1 test-only mismatch is fixed.

## [0.4.0] - 2026-10-13

### Added
- `susanoo init --enforce --enforce-scope settings` puts the enforcement hooks in `.claude/settings.local.json` instead of the skill, so the gates also apply in sessions resumed with `claude --resume` or `--continue`, and compaction recovery works without a manual snippet. Only Susanoo's own hook entries are added or removed and the rest of the file is kept; a file that is not valid JSON, has an unexpected shape, or is a symbolic link stops `init` before anything changes. Because Claude Code does not deduplicate identical hooks, `init` refuses any result that would put the gates in two places (for example a modified skill that still has hooks), and `susanoo doctor` reports where the hooks are and warns if it finds them in more than one place. Switching back to the skill scope keeps the compaction hook. The default scope stays `skill`, and the choice is kept for later `init` runs.
- `scripts/live_enforcement_check.py --scope settings` runs the live checks with settings-scoped hooks.

## [0.2.0] - 2026-10-13

### Added
- Opt-in workflow enforcement (`susanoo init --enforce`): hooks registered by the `/susanoo` skill add a plan-approval gate for edits, approval integrity, shell-write and irreversible-action confirmation, and an evidence gate on `Stop` with loop protection. Routes are bound to the Claude Code session that created them.
